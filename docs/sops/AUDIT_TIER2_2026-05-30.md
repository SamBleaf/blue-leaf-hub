### CRIT-T2-001 — Weekly Update: wrong body field names (11-03 TC-01, TC-03, TC-04 all FAIL)

**SOP:** `portal_add_weekly_update.md` — SOP 11-03  
**Affected TCs:** TC-01, TC-03, TC-04  
**Severity:** CRITICAL — admin cannot create a weekly update through the documented interface

**Expected (SOP says):**
- `POST /api/portal/admin/updates` body: `{ projectId, title, summary, photos?: [] }`
- Required fields: `projectId`, `title`, `summary`
- TC-01 expects response: `{ ok: true, update: { id, title, summary, publishedAt } }`
- TC-03 expects `PATCH /api/portal/admin/updates/:updateId` returns `{ ok: true }`

**Actual (code does):**
- `portalRoutes.mjs:332` destructures: `const { projectId, weekOf, headline, body, authorName, published, videoUrl } = req.body || {};`
- `portalRoutes.mjs:333`: required: `"projectId, weekOf, headline, body required"` — `weekOf` is REQUIRED but not documented at all
- `title` and `summary` arrive as `undefined` → 400 every time
- `portalRoutes.mjs:350`: response is `return res.json(rowToCamel(data))` — bare row, no `ok`, no `update` wrapper
- `portalRoutes.mjs:375`: PATCH also returns bare `rowToCamel(data)`, not `{ ok: true }`
- DB columns are `week_of`, `headline`, `body`, `author_name`, `published` — not `title`/`summary`/`published_at`/`created_by`

**Root cause:** `portalRoutes.mjs:332–350`  
The SOP was drafted with invented field names (`title`, `summary`) that don't exist in the route or the DB schema.

**Impact:** Admin staff typing weekly updates through the Portal Admin UI would get a 400 every single time they click Save. The update feature is non-functional as documented.

**TC verdicts:** TC-01 FAIL, TC-02 SKIP (portal home read), TC-03 FAIL, TC-04 FAIL, TC-05 SKIP, TC-06 SKIP

### CRIT-T2-002 — Decision Respond: wrong field name and wrong values (11-05 TC-03, TC-04 FAIL)

**SOP:** `portal_add_decision.md` — SOP 11-05  
**Affected TCs:** TC-03, TC-04  
**Severity:** CRITICAL — client cannot approve or reject decisions through the documented interface

**Expected (SOP says):**
- Client responds via: `POST /api/portal/:token/decisions/:decisionId/respond`
- Body: `{ response: 'approved' | 'rejected', note? }`
- TC-03: `{ response: 'approved' }` → status = 'approved'
- TC-04: `{ response: 'rejected', note: 'Would prefer Option B' }` → status = 'rejected', `client_note` stored

**Actual (code does):**
- `portalRoutes.mjs:1180`: `const action = req.body?.action;`
- `portalRoutes.mjs:1181`: `const statusMap = { approve: "approved", decline: "declined", info: "info_requested" };`
- `portalRoutes.mjs:1183`: `if (!status) return res.status(400).json({ ok: false, error: "Invalid action" });`
- `portalRoutes.mjs:1198`: `client_note: req.body?.clientNote || null`

**Field name mismatches:**
| SOP claims | Code reads | Verdict |
|-----------|-----------|---------|
| `response` | `action` | FAIL — wrong key |
| `'approved'` | `'approve'` | FAIL — wrong value |
| `'rejected'` | `'decline'` | FAIL — wrong value (and status would be 'declined' not 'rejected') |
| `note` | `clientNote` | FAIL — wrong key |

**Additional finding (MEDIUM):** SOP 11-05 automation notes say `POST /api/portal/admin/decisions` body is `{ projectId, title, description, dueDate? }`. Code at `portalRoutes.mjs:509` also requires `type`:
```js
if (!projectId || !type || !title) return res.status(400).json(..., "projectId, type, title required");
```
`type` is not documented in the SOP at all — omitting it causes a 400.

**Root cause:** `portalRoutes.mjs:1180–1183`  
SOP was drafted with an invented `response` key. The route uses `action` with different value strings.

**Impact:** Clients who tap Approve or Reject in their portal get HTTP 400 "Invalid action" unless the frontend code sends the right keys. If the frontend was coded to the SOP spec rather than the actual route, decisions are permanently broken.

**TC verdicts:** TC-01 FAIL (missing type), TC-02 PASS, TC-03 FAIL (response/action), TC-04 FAIL (response/action), TC-05 PASS, TC-06 PASS

### CRIT-T2-003 — Variation: wrong endpoint, wrong field names, wrong data model (11-06 all key TCs FAIL)

**SOP:** `portal_variation.md` — SOP 11-06  
**Affected TCs:** TC-01, TC-02, TC-03, TC-04  
**Severity:** CRITICAL — variation feature documented against the wrong endpoint and wrong table

**Expected (SOP says):**
- `POST /api/portal/admin/claims` body: `{ projectId, description, amount, reason? }`
- Required: `projectId`, `description`, `amount`
- TC-01: new row in claims table with `status = 'pending'`, `amount = 450`
- TC-02: variation appears in `GET /api/portal/:token/budget` as a variation
- TC-03: Missing `description` → HTTP 400

**Actual (code does):**

`POST /api/portal/admin/claims` (`portalRoutes.mjs:533`):
```js
const { projectId, stageName, amount, status, dueApprox, sortOrder } = req.body || {};
if (!projectId || !stageName || amount == null) {
  return res.status(400).json({ ok: false, error: "projectId, stageName, amount required" });
}
```
- Required field is `stageName`, NOT `description`
- No `reason` field
- Default status is `"upcoming"` (line 547), NOT `"pending"`
- This table (`portal_claims`) is for **progress payment claims** (Deposit, Slab, Frame, etc.) — not scope variations

Portal variations use `POST /api/portal/admin/decisions` with `{ type: "variation", costDelta, scheduleDelta }`.

`GET /api/portal/:token/budget` (`portalRoutes.mjs:961–980`):  
- Variations come from `portal_decisions` where `type = 'variation'`
- `portal_claims` data appears separately as `claims` (payment schedule)

**Root cause:** The SOP was drafted confusing `portal_claims` (payment schedule rows: Deposit/Slab/Frame/Lockup/Handover) with the variation tracking mechanism (`portal_decisions` type=variation). These are entirely different tables with different semantics.

**Impact:** Any admin following this SOP to log a variation would:
1. Get a 400 because `description` is not the required field (`stageName` is)
2. Even if they worked around the field name, they'd create a progress-claim row — not a variation
3. The variation would never appear in the budget's variations section since that reads from `portal_decisions`

**TC verdicts:** TC-01 FAIL, TC-02 FAIL, TC-03 FAIL, TC-04 PASS, TC-05 PASS, TC-06 PASS

### CRIT-T2-004 — Messages: wrong field name for both admin and client send (11-07 TC-01, TC-03, TC-05 FAIL)

**SOP:** `portal_send_message.md` — SOP 11-07  
**Affected TCs:** TC-01, TC-03, TC-05  
**Severity:** CRITICAL — both the admin send and client reply fields are documented incorrectly

**Expected (SOP says):**
- Admin sends: `POST /api/portal/admin/builder-messages` body: `{ projectId, message }`
- Client sends: `POST /api/portal/:token/conversations` body: `{ message: 'Thanks, we will be there.' }`
- TC-01: response `{ ok: true }` from builder-messages
- TC-03: client sends `{ message: '...' }`
- TC-05: "missing message field" → HTTP 400

**Actual (code does):**

Admin route (`portalRoutes.mjs:710`):
```js
const { projectId, body, senderName } = req.body || {};
if (!projectId || !body) return res.status(400).json({ ok: false, error: "projectId, body required" });
```
- Field is `body`, NOT `message`
- Response is `return res.json(rowToCamel(data))` — bare row, not `{ ok: true }`

Client route (`portalRoutes.mjs:1126`):
```js
const body = String(req.body?.body || "").trim();
if (!body || body.length > 2000) {
  return res.status(400).json({ ok: false, error: "Message body required (max 2000 characters)." });
}
```
- Client field is also `body`, NOT `message`

DB effects note (`portalRoutes.mjs:716`): column is `sender` (value `"builder"`), NOT `sender_type`.  
The SOP says DB column is `sender_type` — wrong.

**Root cause:** `portalRoutes.mjs:710`, `portalRoutes.mjs:1126`  
SOP uses `message` consistently; the route uses `body` consistently.

**Impact:** Admin message sends arrive with `body = undefined` → `!body` → 400. Client replies similarly break. The messaging feature is non-functional as documented.

**TC verdicts:** TC-01 FAIL (wrong field + response shape), TC-02 PASS, TC-03 FAIL (message vs body), TC-04 PASS, TC-05 FAIL (validation on wrong field), TC-06 PASS

### BUG-T2-005 — Photos upload: wrong request format and wrong storage backend (11-04 TC-01, TC-02, TC-03 FAIL)

**SOP:** `portal_upload_photos.md` — SOP 11-04  
**Affected TCs:** TC-01, TC-02, TC-03

**SOP claims:**
- API: `POST /api/portal/admin/photos/upload` — multipart/form-data with fields `projectId`, `file` (one or more)

- "Files stored in Supabase Storage under `portal-photos/[projectId]/[YYYY-MM-DD]-[filename]`"

**Root cause:** `portalRoutes.mjs:381–441` uses Dropbox/base64 pattern. SOP assumed Supabase Storage/multipart.

**Impact:** Frontend sending multipart would receive a 400 because `contentBase64` is missing. Staff documentation is wrong on the upload mechanism.

**TC verdicts:** TC-01 FAIL (wrong format/fields), TC-02 FAIL (caption works but wrong req format), TC-03 FAIL (multiple photo multi-call, not single multipart), TC-04 PASS (updateId concept correct), TC-05 PASS (projectId validation correct), TC-06 SKIP
