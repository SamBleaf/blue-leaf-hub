# SOP 06-05: Extension of Time (EOT) — Raise, Approve, and Apply

**Module:** Operations → Schedule Manager → Delays tab  
**SOP ID:** 06-05  
**Status:** Draft  
**Priority:** High

---

## 1. Who uses this
Admin (raises and approves EOTs)

## 2. When to use it
When a delay event occurs that is not the builder's fault and justifies extending the contract practical completion date. Common EOT reasons:
- Client-instructed variations that add time to the programme
- Inclement weather beyond what was reasonably anticipated
- Delays in client approvals or documentation
- Delays caused by third parties (council, utilities)

EOTs must be formally raised and approved — they are contractual. Do not adjust task dates manually to cover delays without raising an EOT.

## 3. What this does
Creates a formal EOT claim record with a reason code, description, and number of days claimed. The EOT goes through a simple approval workflow (pending → approved/rejected). Once approved, the EOT can be applied to the schedule — which shifts ALL task dates forward by the approved number of days.

## 4. EOT reason codes
The reason_code field accepts: `inclement_weather`, `client_variation`, `client_delay`, `third_party`, `supply_delay`, `other`

## 5. Step-by-step process

**Raising an EOT:**
1. Navigate to Operations → Schedule → **Delays** tab
2. Click **+ Raise EOT**
3. Fill in:
   - **Reason code** — select from the dropdown (required)
   - **Description** — plain English explanation of the delay event (e.g. "3 weeks of rain in June prevented concrete pours and frame erection")
   - **Days claimed** — the number of calendar days extension requested (required)
4. Click **Raise** — EOT is created with `status = 'pending'`

**Approving or rejecting an EOT:**
1. On the Delays tab, find the EOT with status "Pending"
2. Click the EOT to review
3. To approve: enter the **Days approved** (may differ from days claimed), click **Approve**
4. To reject: click **Reject**
5. Status updates to `approved` or `rejected`

**Applying an approved EOT to the schedule:**
1. Find the approved EOT on the Delays tab
2. Click **Apply to schedule**
3. Confirm — this shifts every task's start and end date forward by `days_approved` calendar days
4. The practical completion date extends accordingly
5. EOT `applied_at` is recorded

## 6. What happens when an EOT is applied

- Every `schedule_tasks` record for the project has its `start_date` and `end_date` shifted by `days_approved`
- The `schedule_eot.applied_at` is set to now
- The EOT cannot be applied again (one-time operation)
- The baseline dates (if locked) remain unchanged — the drift will now correctly show the EOT-caused shift

## 7. Common mistakes

| Mistake | Why it happens | How to avoid it |
|---------|---------------|-----------------|
| Applying an EOT twice | Clicking Apply again thinking it didn't work | Applied EOTs cannot be applied again — check the Delays tab for `applied_at` |
| Setting days_approved higher than days_claimed without justification | Rounding up | Approved days should be ≤ claimed days unless there's a documented reason |
| Adjusting task dates manually instead of raising an EOT | Quicker | Manual date adjustments don't create a contractual record. Always raise a formal EOT for legitimate delay events. |

## 8. Troubleshooting

| Problem | Solution |
|---------|----------|
| "EOT must be approved before applying" error | The EOT is still in pending status — approve it first |
| "No approved days set" error | Enter `days_approved` when approving |
| Apply button disabled | Check if the EOT has already been applied (`applied_at` is set) |

## 9. Automation notes
- Raise: `POST /api/schedule/:projectId/eot` with `{ reason_code, description, days_claimed }` → creates record with `status = 'pending'`
- Approve/reject: `PATCH /api/schedule/:projectId/eot/:eotId` with `{ status: 'approved', days_approved }` or `{ status: 'rejected' }`
- Apply: `POST /api/schedule/:projectId/eot/:eotId/apply` — loops all active tasks, adds `days_approved` to both `start_date` and `end_date`, sets `applied_at`
- Validation: apply endpoint returns 400 if `status !== 'approved'` or `days_approved` is null/zero
