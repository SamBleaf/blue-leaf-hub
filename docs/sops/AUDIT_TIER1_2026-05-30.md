## CRITICAL BUGS

### CRIT-001 — RFQ Package routes have NO authentication: all data publicly accessible

**Severity:** CRITICAL — Security vulnerability  
**SOPs affected:** 04-01 through 04-09 (all RFQ Engine SOPs)  
**Test cases blocked:** All TC-01 through TC-05 for every RFQ SOP where the test involves auth

**Expected:** Every route requires a logged-in Admin user (`requireAuth` middleware)  
**Actual:** Zero routes in `rfqPackageRoutes.mjs` use `requireAuth`. All RFQ Package data is accessible without a session token.

**Routes exposed unauthenticated:**
```
GET    /api/rfq-packages
POST   /api/rfq-packages
GET    /api/rfq-packages/:packageId
PATCH  /api/rfq-packages/:packageId
DELETE /api/rfq-packages/:packageId
POST   /api/rfq-packages/:packageId/scopes
PATCH  /api/rfq-packages/:packageId/scopes/:tradeId
DELETE /api/rfq-packages/:packageId/scopes/:tradeId
POST   /api/rfq-packages/:packageId/scopes/:tradeId/recipients
PATCH  /api/rfq-packages/:packageId/recipients/:recipientId
POST   /api/rfq-packages/:packageId/scopes/:tradeId/send
POST   /api/rfq-packages/:packageId/recipients/addendum
GET    /api/rfq-packages/:packageId/trade-coverage
... (all routes in this file)
```

**Root cause:** `rfqPackageRoutes.mjs` does not import `requireAuth` and never calls it. Every `app.get(...)`, `app.post(...)`, `app.patch(...)`, `app.delete(...)` in the file is missing the middleware.

**Impact:** Anyone with the server URL can read, create, update, or delete RFQ packages, trade scopes, recipients, and trigger email sends without logging in. This is a live production security vulnerability. All test cases in SOPs 04-01 through 04-09 that verify "Admin can..." implicitly require authentication that does not exist.

**Fix:** Add `requireAuth` to every route registration in `rfqPackageRoutes.mjs`. Pattern:
```js
app.get("/api/rfq-packages", requireAuth, async (req, res) => { ... });
```

### CRIT-002 — Accept Quote does NOT mirror to rfqs table: SOP 04-08 TC-01 always fails

**Severity:** CRITICAL — Data integrity bug  
**SOP:** 04-08 (Accept a Quote)  
**Test case:** TC-01 step 7: "Expected DB: `rfqs.status = 'accepted'` (if rfq_id linked)"

**Expected:** When `rfq_recipients.status` is set to `accepted`, the linked `rfqs` row mirrors the status to `rfqs.status = 'accepted'`.  
**Actual:** The `rfqs` table is never updated on acceptance. It stays at its prior status (`sent`, `received`, etc.).

**Root cause** (`rfqPackageRoutes.mjs`, recipient PATCH handler ~line 481):
```js
// Only these statuses are mirrored to rfqs:
if (patch.status === "received") rfqPatch.status = "received";
if (patch.status === "declined") rfqPatch.status = "declined";
// MISSING:
// if (patch.status === "accepted") rfqPatch.status = "accepted"; ← never written
```

The accepted branch simply doesn't exist in the mirroring logic.

**Impact:** `rfqs` quote tracker permanently shows wrong status after acceptance. Any reporting or legacy workflow reading `rfqs.status` to find accepted quotes will return zero results. SOP 04-08 TC-01 post-test checklist item "rfqs row mirrors the acceptance" always fails.

**Fix:** Add the missing branch in `rfqPackageRoutes.mjs` recipient PATCH handler:
```js
if (patch.status === "accepted") {
  rfqPatch.status = "accepted";
  rfqPatch.quote_amount = patch.quote_amount ?? cur.quote_amount;
}
```

### CRIT-003 — Hold Invoice endpoint does not exist: SOP 09-05 entire test script is void

**Severity:** CRITICAL — Feature does not exist  
**SOP:** 09-05 (Put an Invoice on Hold)  
**Test cases blocked:** TC-01, TC-02, TC-03, TC-04 (all 4 test cases)

**Expected (per SOP 09-05 Section 11):**
```
API: PUT /api/financial-documents/:id/hold
Body: { hold_reason: string, follow_up_date?: date }
Sets: financial_documents.status = 'on_hold'
Sets: financial_documents.dispute_reason = hold_reason
Sets: financial_documents.dispute_follow_up_date = follow_up_date
```

**Actual:** No such endpoint exists anywhere in `financeRoutes.mjs` or `financeCCRoutes.mjs`. Additionally, the URL prefix in the SOP is wrong:
- SOP claims: `/api/financial-documents/:id/hold`  
- Actual API prefix: `/api/finance/documents/:id/...` (note: `finance/documents`, not `financial-documents`)

The `PATCH /api/finance/documents/:id` endpoint does allow `{ status }` to be updated but:
1. Does not accept or store `hold_reason`
2. Does not accept or store `follow_up_date`
3. Has no validation that requires a reason before holding

**Impact:** The entire Hold Invoice workflow described in SOP 09-05 is not implemented. Users clicking a "Hold" button in the UI would either get a 404 or route to the wrong endpoint. All TC-01–TC-04 test cases fail completely. The "Requires Action" section in Job Command Centre cannot show held invoices with follow-up dates as documented.

**Fix:** Either (a) build the dedicated hold endpoint, or (b) update PATCH `/api/finance/documents/:id` to accept `hold_reason` and `follow_up_date` when `status = "on_hold"`, and update SOP 09-05 to reflect the correct URL and approach.

### BUG-005 — Duplicate `command-centre` route: financeRoutes.mjs version queries non-existent column

**Severity:** Medium — Silent data error in the command-centre query  
**SOP:** 09-07 (Job Command Centre Overview)  
**Test case:** TC-01 (pending approvals list shows invoices)

**Issue:** `GET /api/finance/jobs/:id/command-centre` is registered in **two files**:
1. `financeRoutes.mjs` ~line 1168 (earlier registration)
2. `financeCCRoutes.mjs` ~line 353 (later registration — wins in Express)

The `financeRoutes.mjs` version queries:
```js
sb.from("financial_documents")
  .select("id, supplier_name, total_amount, ...")  // ← "total_amount" doesn't exist
  .eq("job_id", id).eq("status", "pending_approval")
```

The actual column is `amount_total`, not `total_amount`. This Supabase query silently returns `null` for that column.

**Impact:** Because Express registers routes in order and the `financeCCRoutes.mjs` version registers last, the correct version is active. The `financeRoutes.mjs` version is dead code. However, if route registration order ever changes, the pending approvals list will return `null` amounts for all invoices. The dead code is a maintenance hazard.

**Fix:** Remove the duplicate `command-centre` route from `financeRoutes.mjs` (lines ~1168–1299). The `financeCCRoutes.mjs` version is correct and complete.

### BUG-006 — WIPAA endpoint 307 redirects: SOP 09-11 tests fail unless redirect is followed

**Severity:** Medium — Test script references wrong endpoint  
**SOP:** 09-11 (WIPAA Review)  
**Test cases:** TC-01, TC-02 (load WIPAA data)

**Issue:** `financeRoutes.mjs` line ~847:
```js
app.get("/api/finance/jobs/:id/wipaa", requireAuth, async (req, res) => {
    return res.redirect(307, `/api/finance/jobs/${req.params.id}/wipaa/current`);
```

### BUG-007 — RFQ Package routes return raw snake_case: frontend reads camelCase

**Severity:** Medium — All RFQ Package data displays incorrectly in the UI  
**SOP:** 04-01 through 04-09 (all RFQ SOPs)  
**Test cases:** Any TC that checks displayed field values

**Issue:** `rfqPackageRoutes.mjs` never calls `rowToCamel()` or `rowsToCamel()` from `apiResponse.mjs`. All `res.json()` calls return raw Supabase snake_case objects:
```js
// Example — return raw data, no camelCase conversion:
return res.json({ ok: true, package: data });  // data has snake_case keys
```

Per CLAUDE.md standards: "Server converts with rowToCamel(row) / rowsToCamel(rows) from apiResponse.mjs before sending. Frontend reads camelCase."

**Impact:** If the RFQ frontend components follow the camelCase convention (reading `rfqPackage.packageId`, `tradeScope.budgetAmount`, etc.), all those reads return `undefined`. Data appears blank or broken in the UI.

**Note:** This bug is somewhat masked because CRIT-001 (no auth) means the routes can be hit without login — but the data shape mismatch will cause display issues regardless once auth is added.

**Fix:** Import and apply `rowsToCamel`/`rowToCamel` from `apiResponse.mjs` at all return points in `rfqPackageRoutes.mjs`.

## LOW BUGS

### LOW-001 — SOP 04-05 doesn't document partial-send scope status behaviour

**SOP:** 04-05 (Send RFQ Emails)  
**Test case:** TC-03 (partial success)

SOP 04-05 TC-03 correctly tests that valid recipients succeed and invalid ones fail. However, the SOP doesn't document an important code behaviour: **scope status only updates to `sent` if ALL recipients succeed**.

In `rfqPackageRoutes.mjs` (~line 435):
```js
const allSent = results.every(r => r.ok);
if (allSent) {
  await sb.from("rfq_trade_scopes").update({ status: "sent" }).eq("id", tradeId);
}
```

If one recipient fails, the scope stays in `draft` status even though other recipients got the email. The SOP and test script don't mention this. Staff may be confused when a scope shows `draft` after a partial send.

**Fix:** Add a note in SOP 04-05 Section 7 and TC-03: "If any recipient fails, the trade scope status remains `draft`. You must fix the failing recipient address and resend."

**SOP:** 04-09 (Issue an Addendum)

## STANDARDS VIOLATIONS

### STDS-001 — rfqPackageRoutes.mjs violates all three response standards

**File:** `server/lib/rfqPackageRoutes.mjs` (entire file)

Three compounded violations:

**1. No requireAuth** (see CRIT-001 above)

**2. Raw `res.json()` instead of `ok()/err()` from apiResponse.mjs:**
```js
// Every error response in the file:
return res.status(400).json({ error: "recipients required" });   // ← never ok: false
return res.status(404).json({ error: "Package not found." });    // ← should be err(res, 404, ...)
return res.json({ ok: true, package: data });                    // ← bypasses ok() helper
```

**3. Raw Supabase error strings reach the browser:**
```js
return res.status(502).json({ ok: false, error: e?.message || String(e) });
// e.message can be a raw Postgres error with internal DB details
```

Per CLAUDE.md standards: "Never expose raw Supabase/Postgres error strings — use translateDbError(error)."

**Fix:** Refactor all route handlers in `rfqPackageRoutes.mjs` to import and use `ok`, `err`, `rowsToCamel`, `translateDbError` from `./apiResponse.mjs`.

---

### STDS-002 — financeRoutes.mjs exposes raw DB errors in multiple routes

**File:** `server/lib/financeRoutes.mjs`

Multiple routes use the pattern:
```js
if (error) return res.status(500).json({ ok: false, error: error.message });
```

This exposes raw Supabase/Postgres error messages directly to the browser. Examples:
- `/api/finance/documents/:id/approve` (~line 758)
- `/api/finance/documents/:id/reject` (~line 810)
- `/api/finance/jobs/:id/budget/:trade_category_id` (~line 1413)
- Several stats and list routes

The `financeCCRoutes.mjs` version of many routes has the same pattern.

**Fix:** Replace `error.message` with `translateDbError(error)` at all Supabase error return points, or wrap in a plain-English message.
