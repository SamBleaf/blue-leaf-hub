# Client Portal v2 — Hostile Security Review

**Reviewer stance:** Red-team. Goal: expose data that must never reach a client (cross-project data, builder cost/margin/internal notes, hidden documents, supplier pricing) and break contractual/approval integrity.

**Scope reviewed:** `requirePortalAuth.mjs`, `portalV2Routes.mjs`, `portalV2AdminRoutes.mjs`, `clientPortalApi.js`, `portalRoutes.mjs` (legacy token), `requireAuth.mjs`, `authRoutes.mjs` (invite flow), migration `103_client_portal_v2.sql`, migration `044_rls_require_authenticated.sql`, migration `027_client_portal.sql`.

**Verdict:** The JWT portal API (`portalV2Routes.mjs`) is, in isolation, well-built — every route is scoped by `req.portalSession.projectId`, field allowlists are disciplined, and contractual writes are double-gated and audited. **But the portal is not deployed in isolation.** It grafts real Supabase `authenticated` accounts (role `client`) onto a database whose RLS was explicitly designed for a *single-tenant* staff app (migration 044). The result is two CRITICAL exposure paths that completely bypass the carefully-built field allowlists. A logged-in client can read **every project, every job's cost data, every other client's PII, and the entire CRM** directly — the allowlists are decorative against this attacker.

## Root cause (one sentence)

The portal's per-project access boundary is enforced **only inside `requirePortalAuth` + the service-role API**, but issuing clients a real `authenticated` Supabase identity (with a `user_profiles` row and the `authenticated` RLS grant from migration 044) hands them a second, unguarded door — the anon-key client and the ~360 bare-`requireAuth` staff endpoints — that the field allowlists never see.

## Remediation priority

1. **#1 / #14 / #2 (CRITICAL, same week):** Decide the client identity model. Cleanest: clients get an auth account but are **denied** by every `authenticated` RLS policy and by `requireAuth` (reject `role:'client'`); all client data flows exclusively through the service-role portal API. This is a DB-policy + one-middleware-line change and it closes the largest holes.
2. **#7 / #15 (CRITICAL/HIGH):** Kill or login-gate the legacy token write + disable legacy token on v2 projects.
3. **#5 / #6 (HIGH):** Allowlist the legacy token reads; never emit `*_ex_gst`/`cost_delta`.
4. **#11 (HIGH):** Enforce portal sub-roles on contractual writes.
5. **#9 caveat / #12 / #16 (MEDIUM-LOW):** Confirm supersede flips `client_visible`; add a DB trigger for audit immutability; drop `portal_token` from responses.

---

## 4-line summary

The JWT portal API itself is solid: every route is project-scoped via `req.portalSession.projectId`, field allowlists correctly strip cost/margin/internal-notes, and contractual writes are double-gated and audited. But clients are issued real `authenticated` Supabase accounts, and migration 044 grants `authenticated` full RLS access to every business table — so a logged-in client can read all projects, all job cost data, every other client's PII, and the entire CRM directly via the anon key, plus call ~360 staff endpoints gated only by `requireAuth` (no role check). The legacy `/api/portal/:token/*` surface remains live in parallel, leaking `amount_ex_gst`/`builder_reasoning` to anonymous token holders and allowing **unauthenticated** variation approval. Portal sub-roles (architect/accountant) are never enforced — any active membership row gets full financial and contractual access.

**Critical findings: 4** (cross-project enumeration via RLS #1, client access to staff APIs #2, anonymous contractual write #7/#13, anon project enumeration #14 — #1 and #14 share a root cause).
