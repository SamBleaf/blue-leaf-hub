# Client Portal v2 — Failure Analysis (Adverse / Red-Team)

**Stance:** Hostile red-team. Every claim is grounded in the actual code (file:function/line). The goal is to find what breaks, what is ambiguous, and what could cause a **dispute with a $2m client** before this ships. Where something is genuinely well-built it is noted briefly; the bulk of this document is failure modes.

**Scope reviewed:** `server/lib/{requirePortalAuth,portalV2Routes,portalV2AdminRoutes,portalIntegration,portalSync,authRoutes}.mjs`, `server/lib/financeCCRoutes.mjs` (sync call-sites), `server/dev-api.mjs` (cron), `src/lib/clientPortalApi.js`, `src/pages/clientportal/*`, `supabase/migrations/{044,103,103b}`.

**Go-live context that amplifies everything below:** ONE production DB, no staging; migration 103 is **manual paste, not yet applied**; everything gated behind `projects.portal_v2_enabled`; **no e-signature** (approvals are timestamp + account only); `resolveClientProjectId` reads `projects` via the **anon client under RLS**.

## CRITICAL FINDINGS (must fix before any client logs in)

### C-1. A logged-in client can read (and write/delete) the ENTIRE business database via the anon Supabase client
This is the headline finding and it is not subtle.

- `authRoutes.mjs` `accept-invite` (line 276 `sb.auth.admin.createUser`) gives every portal client a **real Supabase `authenticated` session** — the same role grade as staff.
- `044_rls_require_authenticated.sql:41` sets the projects policy to `authenticated_all_projects ... FOR ALL TO authenticated USING (auth.uid() IS NOT NULL) WITH CHECK (auth.uid() IS NOT NULL)`. The same pattern is applied to `jobs` (19), `subcontractors` (20), `rfqs` (21), `cost_intelligence` (22), `leads` (82), `fee_proposals` (49), `site_diary` (66), `schedule_tasks` (60), `purchase_orders` (42), and more.
- The comment in 044 says *"single-tenant app … any signed-in user can access all rows."* The portal breaks that assumption: it introduces **external, untrusted users** into the `authenticated` role. The whole design was written for staff-only auth.
- `clientPortalApi.js:resolveClientProjectId` (line 63) **proves clients use this path** — it queries `projects` directly through the anon client and relies on RLS. That query only "works" because RLS lets the client read projects… which means it lets them read **every** project, not just theirs (the `.eq("portal_client_email", email)` is an application filter the client can simply remove).

**Attack:** client opens devtools, lifts `VITE_SUPABASE_ANON_KEY` from the JS bundle (CLAUDE.md itself notes the anon key is in the bundle), uses their own valid session token, and runs `supabase.from('jobs').select('*')`, `from('cost_intelligence')`, `from('leads')`, `from('fee_proposals')`. They get **every other client's contract value, every builder cost/margin, the entire sales pipeline, every subbie quote.** They can also `UPDATE`/`DELETE` those rows (`FOR ALL`, `WITH CHECK (auth.uid() IS NOT NULL)`).

**Why the server-side allowlists do NOT save you:** `portalV2Routes.mjs` field allowlists (lines 36–66) only constrain what the *portal API* returns. They are irrelevant — the client bypasses the API entirely and talks to Postgres directly with a privileged session.

**Severity: CRITICAL (catastrophic data breach + tamper).** This alone blocks go-live.

**Fix:** Clients must NOT hold a general `authenticated` session, OR every `authenticated_all_*` policy must be rewritten to exclude client users (e.g. gate on a staff-only claim / `user_profiles.role <> 'client'`, or move clients to a distinct role/separate Supabase project). The portal API already uses the service role and its own middleware — clients should never touch Postgres directly. `resolveClientProjectId` should move server-side (a `/api/portal/my-projects` endpoint) so the frontend never needs client RLS read on `projects` at all.

### C-2. `/api/cron/portal-sync` is unauthenticated and mutates every project
`dev-api.mjs:1568` — `app.post("/api/cron/portal-sync", async (_req, res) => …)`. No secret, no `requireAuth`, no header check (`_req` is literally unused). `runPortalNightlySync` (`portalSync.mjs:167`) iterates **all** portal-enabled projects and **writes**: flips `client_selections.status → 'overdue'` (line 148), rewrites `portal_milestones.is_current` / `achieved_at` / `confidence` (123–125), and flips `client_actions.status → 'overdue'` (152).

**Attack:** anyone on the internet POSTs this URL on a loop. Result: continuous DB writes across every project (DoS / cost), and they can force a client's "My Actions" red/overdue state or move the current-stage flag at will. Combined with C-1's data exposure, an attacker can also confirm which projects exist.

**Severity: CRITICAL.** **Fix:** require a cron secret (`x-cron-secret` compared to env) or `requireAuth` admin, same as the other cron routes should have.

### C-3. Variation approval audit is the legal record — but the design is timestamp-only AND the two approval paths can diverge
There is **no e-signature** (stated). The "signature" is `portal_audit_logs` row + `responded_at` + `client_user_id` (`portalV2Routes.mjs:393–420`). Two structural problems make this challengeable in a dispute:

1. **The audit log is not actually immutable in practice.** Migration 103 omits UPDATE/DELETE *policies* on `portal_audit_logs` (good, lines 357–361) — but **every portal write uses the service-role key, which bypasses RLS entirely** (`requirePortalAuth.mjs:15` header comment confirms this). Staff/server code can `UPDATE`/`DELETE` audit rows freely. So the "immutable contractual record" is immutable only against a class of callers that never touches it anyway. A client's lawyer will argue the builder could have fabricated/edited the approval. There is no hash chain, no append-only enforcement at the engine level, no third-party timestamp.
2. **Two writers, no lock.** A client approving in the portal (`/variations/:decisionId/respond`) and staff signing in Finance (`financeCCRoutes.mjs:1958 /sign`) both mutate `job_variations` AND the portal decision. They are not serialized. See C-4.

**Severity: CRITICAL (contractual enforceability).** **Fix:** real e-signature or, at minimum, (a) a tamper-evident audit (hash-chained or write to an append-only store the service role can't edit), (b) capture the rendered document version + a client-typed full-name acknowledgement, (c) email the client a copy of what they approved at approval time.

### C-4. Finance "sign" and client "approve" race / collide — and the documented staff workflow 400s after a client approves
- Client approves via portal: `portalV2Routes.mjs:427` sets `job_variations.status = 'signed'`, `signed_date = now`.
- Finance `/sign` (`financeCCRoutes.mjs:1963`) **requires** `existing.status === 'sent_to_client'` and otherwise returns *"Only variations sent to client can be signed. Send the variation first."*
- The Finance sign route comment literally says *"admin marks as signed after client approval"* — i.e. the intended workflow is client approves → admin signs. **But the portal already flipped the status to `signed`, so the admin's sign call now 400s.** Staff will see a confusing error and may "re-send" the variation (which is allowed for `draft`/`rejected` only — also blocked), or assume it failed.
- Conversely if staff sign **first**, the portal decision is set to `approved` by `syncVariationSigned` (`portalIntegration.mjs:133`), and then the client clicking Approve hits the `status !== 'pending'` guard (`portalV2Routes.mjs:386`) → 409 *"already responded to."* The client who was told "please approve in the portal" now sees an error and thinks the system is broken.
- Neither path writes the **other** side's side-effects: the portal `/respond` path also separately archives a PDF to Documents (lines 437–448) AND `syncVariationSigned` archives a PDF (`portalIntegration.mjs:159`). The portal path's insert has **no idempotency guard** (it always inserts), while the sync path checks for an existing doc — so the **Documents tab can show a duplicate variation PDF** if both fire.

**Severity: CRITICAL (dispute + broken workflow + duplicate docs).** **Fix:** single state machine; make `/sign` tolerate `signed` when it originated from the portal; dedupe the document insert in `/respond` the way `syncVariationSigned` does.

## WHAT IS GENUINELY GOOD (brief)

- **Field allowlists** (`portalV2Routes.mjs:36–66`) are disciplined: builder cost / `amount_ex_gst` / `internal_notes` are excluded from every client-facing read **through the API**. (Undermined by C-1, not by the API itself.)
- **`requirePortalWrite` fail-safe** (`requirePortalAuth.mjs:139`) correctly blocks anonymous-token callers from contractual writes by default, on every project.
- **Audit-before-respond with rollback**: the variation respond route rolls the decision back to `pending` if the audit insert fails (`portalV2Routes.mjs:416`) — it won't record an un-audited approval. Good instinct (weakened only by service-role mutability, C-3).
- **Idempotent sync upserts** keyed on `job_variation_id`/`progress_claim_id` prevent duplicate shadow rows (`portalIntegration.mjs`).
- **`is_active !== true` fail-safe** (`requirePortalAuth.mjs:57`) treats NULL/missing as no-access — correct.
