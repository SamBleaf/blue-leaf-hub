# Client Portal v2.0 — Feature Register & Red-Team Audit

**Audit date:** 2026-06-21
**Auditor stance:** Hostile red-teamer. Every row is grounded in actual code (file:function/line). The "Risks" column is the point of this document. "Good" callouts are kept brief.
**Build state factored in:** Migration 103 NOT yet applied to the single production DB (manual dashboard paste only, no staging). Everything gated behind `projects.portal_v2_enabled`. No e-signature — approvals are timestamped/account-recorded. `resolveClientProjectId` reads `projects` via the anon client (RLS-dependent).

**Verdict up front:** The portal is architecturally clean (field allowlists, service-role enforcement boundary, audit-before-respond, fail-safe token write block). But it is functionally incomplete and operationally fragile in ways that will surface on the *first* real client: **site photos never load**, **no notification is ever sent** (the whole notifications table is dead), **the unsubscribe/cron endpoints are unauthenticated**, **the "no e-signature" disclaimer is contradicted by the UI**, and **a supervisor literally cannot invite a client**. Detailed below.

---

## Legend

- **Role:** `client(jwt)` = logged-in Supabase client; `token` = anonymous legacy share-link; `staff` = admin/supervisor/employee; `system` = cron/finance hook.
- File refs are relative to repo root. Line numbers are at audit time.

## 9. Coverage Gaps — intended UX (plan §3, §0.12, §0.13) NOT implemented in code

1. **Site photos on Home AND Journey are broken** — `/api/portal/media/:id` requires `?token=`; the v2 `<img>` tags send none → all photos 404. Plan §Home explicitly specs a "Recent photos from site (8 this week)" grid; `ClientHome` doesn't even render it. (Highest-impact gap.)
2. **Client notifications do not exist** — `portal_notifications` has zero inserts; no email/in-app/SMS fires to the client for variations, selections due, claims, updates, meetings, or message replies. Plan §0.13.5 + the whole notification schema are unrealised. Plan-specified `noreply@` sender + portal deeplink for message notifications: not implemented (uses default sender, no deeplink).
3. **No e-signature, but the UI/data say otherwise** — plan acknowledges "no e-signature; approvals timestamped/account-recorded," yet variation approval writes `job_variations.status='signed'`+`signed_date` (a contractual signature on the canonical record) while telling the client "Blue Leaf will issue a signed variation document separately." `portal_documents.signature_required`/`signed_at` columns and the `document_signature` action_type imply a signing flow that does not exist.
4. **Build Health Score not a standalone prominent card** — plan §0.13.3 wants a forward-to-family standalone status card; code only renders confidence as a chip inside the stage card, hidden entirely in pre-construction and when no current stage exists.
5. **Stage preview / "what to expect"** — column + admin field exist, but only renders for `upcoming` stages that have a current/achieved sibling; pre-construction-only projects (the §0.12.1 scenario) often won't show it.
6. **Selections lead-time risk** — `order_by_date` has no auto-calc (`fixing_start - lead_time_weeks`) and no admin input field; the "Order by X to avoid fixing delay" warning is dead unless a value is hand-set in the DB. Plan §0.12.4 calc unimplemented.
7. **Referral/review (§0.12.6)** — no `settings.google_review_url` (review link has empty placeid → broken), no `crm_interaction` testimonial-consent row, no Sam task on "I'd love that". It's a bare mailto.
8. **Admin cannot publish documents** — no documents UI in `PortalV2Admin.jsx`; the contract, approved plans, and engineering PDFs the plan's Documents page promises can only enter via finance auto-archive. The "smart archive" is mostly empty by design.
9. **Admin cannot set builder_reasoning on variations** — `PATCH /decisions/:id` exists but has no admin UI; §0.12.5 is backend-only.
10. **Draft/review workflow for updates** — schema supports `draft/reviewed/published`; UI always publishes. No staff review gate.
11. **Dual approval** — `requires_dual_approval`/`second_approval_*` columns never enforced; a single client approves any-value variation alone.
12. **Selection undo / variation re-open** — both are one-way from the client side; mistakes require a phone call (the exact thing the portal is meant to eliminate).
13. **Post-completion route lockdown** — `journey`/`selections`/`my-home` routes stay reachable by URL regardless of build phase; nav hides but doesn't gate.
14. **Nightly sync isn't scheduled** — runs once at boot + via an unauthenticated public endpoint; no daily trigger wired on Railway.
15. **No project switcher** for multi-project clients; `resolveClientProjectId` silently picks one.
16. **No audit visibility** — `portal_audit_logs` has no read UI; staff/admin actions aren't audited at all. The "contractual immutable log" can't be reviewed without DB access and is missing every non-client mutation.
17. **Supervisor cannot invite clients** — admin console allows supervisors, but `/api/auth/invite` requires `admin`; supervisors get a silent 403.
18. **Selection-decision actions are inert in My Actions** — the plan's "most important page" can't complete a selection inline; it redirects to the Selections board.
19. **RFI / colour approval / handover-item action types** have schema entries but no producer and no client handler.
