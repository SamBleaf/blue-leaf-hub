## Roadmap

# Blue Leaf Hub — Phased Implementation Roadmap

**Goal:** increase usability and fix inter-module workflow friction without rebuilding. Every change respects the Laws (ok()/err()+rowToCamel, camelCase boundary, constants.js enums, Canonical Data Law, roles, migrations in supabase/migrations — next free number is **093**).

**Sequencing logic in one line:** build the *shared primitives and the one money-correctness convergence* first (they underpin everything), then ship the high-frequency usability wins on top of them, then close the integration-trust gap, finishing with consistency polish.

The 47 quick-wins are sprinkled across every phase as "ship-anytime" warm-ups — they are S-effort, mostly independent, and several are the seeds of the larger opportunities (e.g. QW#1/#2 are literally Opportunity #2's first workstream; QW#25/#36 are Opportunity #6's terminology pass). Do the quick-wins in the module a phase is already touching, so you only open each file once.

## Phase 0 — Foundations + free wins (start here)
**Build the shared spine + land the cheap correctness/perf fixes that need no new infrastructure.**

Three small, independently-shippable primitives unblock most of the rest of the program:

1. **`useOptimisticList` hook** (Opp #4 WS1) — lifts the optimistic pattern already hand-rolled in `Workforce.jsx:127` into one reusable hook. Keystone for both responsiveness (Opp #4) and bulk actions feeling instant (Opp #3).

Centralise `RFQ_STATUSES`/`RFQ_STATUS_LABELS`/`RFQ_STATUS_BADGE` and `INTEGRATION_SYNC_STATUSES` in constants.js here (no migration — constants only mirror existing DB CHECK values).

Alongside, land the **pure quick-wins that need no primitive and no migration** — perf and correctness fixes that are safe to ship immediately and reduce noise for later phases.

## Strategy (3 small shared primitives + targeted conversions)

**Primitive A — `useOptimisticList` hook** (`src/hooks/useOptimisticList.js`, new). A thin wrapper over `useState` providing `{ items, setItems, patchOne(id, patch), removeOne(id), addOne(item), replaceOne(id, row), rollback() }`. Snapshots before an optimistic edit; on server error, rolls back and surfaces the error. This is the same shape Workforce already hand-rolls — we lift it into a reusable hook so the other 4 modules adopt one consistent pattern. No new deps.

**Primitive B — `CacheProvider` + `useCachedResource`** (`src/lib/CacheProvider.jsx`, new; wired in `src/App.jsx` alongside the existing `ProjectProvider`). An in-memory `Map` keyed by URL, each entry `{ data, fetchedAt, ttl }`, with `invalidate(key)` and `invalidatePrefix(prefix)`. Reads serve cache if `Date.now() - fetchedAt < ttl`; mutations call `invalidate()`. Used for the genuinely static/slow-changing reference data the audit calls out: `/api/sales/reference-projects` (LeadDetail.jsx:1003 — refetched on every stage transition), `trade_categories`, and the active-projects list. TTL constants go in `constants.js` next to the existing exports (e.g. `CACHE_TTL = { REFERENCE_PROJECTS: 86_400_000, TRADE_CATEGORIES: 86_400_000, PROJECTS: 300_000 }`). Mirrors `ProjectContext`'s localStorage approach but generalised; optional localStorage persistence for the 24h-TTL static sets.

**Primitive C — targeted-refetch convention**. Where optimistic merge alone is unsafe (server computes derived values the client can't predict), refetch only the affected entity/IDs instead of the whole list. The server already returns the updated row in some places (`salesRoutes.mjs:398` returns `{ lead: data }`) — use it directly. Where it doesn't (`scheduleRoutes.mjs:1134` returns only `{ updated: updatedIds }`), either (a) extend the endpoint to return the updated rows, or (b) optimistic-merge the edited task + refetch only `updatedIds`.

## The pattern to standardize (3 layers, usability-first, NOT a rebuild)

1. **Server response flag (no schema needed for most).** When a route does an integration side-effect that can fail independently of the primary save, stop swallowing it. Return a small, predictable object via the existing `ok()` helper:
   ```js
   ok(res, { entry, integration: { dropbox: { ok: false, error: "Dropbox token expired" } } });
   ```
   Replace the bare `console.warn` in the catch with: still log, but also capture the message into a variable and include it in `integration`. The primary record still saves (so we never block the user's work) — we just stop *lying* about the side-effect.

2. **Persist the failure where a record exists** (so it survives reload and enables Retry). Site Diary, WHS compliance, WHS incidents, and fee proposals all already have a row + a `dropbox_path`/`dropbox_pdf_path` column. Add a sibling `*_sync_error text` column (mirroring `timesheets.buildexact_sync_error`) so a null path + non-null error = "needs retry", and a null path + null error = "not attempted". This is the only place a migration is needed, and it's purely additive.

3. **UI: warning badge + Retry, reusing the Workforce idiom.** Extract the Workforce badge (`⚠ Sync failed` + tooltip + Retry) into one shared component `src/components/IntegrationStatusBadge.jsx` and drop it into Site Diary entry rows, WHS compliance/incident rows, and the fee-proposal send result. Change the unconditional success toasts to branch on `j.integration.dropbox.ok`: "Saved — but PDF not filed to Dropbox (Retry)" vs "Saved. PDF filed to Dropbox."

4. **Retry endpoints.** Each persisted-failure surface gets a tiny `POST .../:id/retry-dropbox` that re-runs only the upload step and clears the error on success — modeled exactly on `/api/workforce/timesheets/:id/sync`.

5. **Settings integration health panel (the audit's "integration audit log").** Add a read-only panel that surfaces (a) the existing IMAP `last` results, (b) counts of unresolved `*_sync_error` rows per surface (cheap `count` queries), and (c) the existing Buildexact webhook events. This makes "something is silently failing" visible at a glance without any new logging infrastructure. A persisted `integration_events` log table is **optional/deferred** — the per-row error columns already give retry + visibility; a central log is a nice-to-have, not required for the win.

## Why this is usability-first and not a rebuild
We change **zero integration logic** — `dropboxUploadBuffer`, `createPurchaseOrder`, `sendPlainMail`, `ImapFlow` all stay exactly as they are. We only (a) stop discarding the error they already produce, (b) thread it through the existing `ok()` envelope, (c) persist it in one additive column, and (d) render the same badge that already ships in Workforce. The Law surface touched is minimal: `ok()`/`rowToCamel` already cover the boundary; new status strings go in `constants.js` (`INTEGRATION_SYNC_STATUSES`).

- Settings shows an Integration health panel with last IMAP poll result, unresolved-failure counts per surface, and Buildexact webhook events — so a silent failure is discoverable in one place.
- Zero changes to the integration clients themselves (dropboxClient, buildexactClient, notifyMail, ImapFlow) — diff is confined to route handlers, one additive migration, FE pages, and one shared component.
- npm run lint and npm run build pass; new status strings come from constants.js (no hardcoded enums); responses use ok()/err()+rowToCamel and camelCase boundary.

**Risks:** - **Behavioral change in WS5 (fee-proposal Buildexact status).** Moving the `buildexact_status:'sent'` stamp to after the sync resolves changes when downstream consumers see 'sent'. Mitigation: keep email-sent and buildexact-sent as distinct states (email succeeds independently); never block the email on the Buildexact result. Verify no consumer treats buildexact_status as a proxy for 'email was sent'.
- **Toast/UX regression risk.** Changing always-green Site Diary/WHS toasts could feel noisier. Mitigation: only downgrade to a warning when the side-effect genuinely failed; the happy path message is unchanged.
- **Retry idempotency.** Re-generating/re-uploading a PDF on retry must be idempotent (autorename + fixed path already handle this) and gated to the same roles as the original action.
- **In-memory IMAP health lost on restart.** WS7 surfaces it but a restart blanks it; acceptable for v1 since per-row error columns are the durable record. Persisted integration_events log explicitly deferred.
- **Stale audit text.** Findings 1.4/4.2 are already fixed in the Workforce path; the plan marks that as reference-only to avoid re-fixing.
- **Scope creep into a logging framework.** Resist building a central integration_events emitter for this opportunity — per-row columns + Settings aggregation deliver the win cheaply.
